# Аудит проекта ToDoro

Проведи полный аудит проекта ToDoro (Python, SQLite, Kotlin). Сначала ничего не меняй — только
анализ и отчёт с приоритетами (критично / важно / желательно), для каждой проблемы: файл и
строка, почему это проблема, как исправить.

Если пользователь передал аргументы (например, `/audit python` или `/audit android`) —
проверь только эту часть.

## Пути и инструменты

- Проект: `D:\Claude\ToDoro`. Python: `%LOCALAPPDATA%\Python\bin\python.exe`.
- Инструменты проверки ставь только с согласия пользователя (`python -m pip install --user ...`).
  Если чего-то нет — скажи, что именно, и предложи установить; не устанавливай молча.
- bandit на Python 3.15 не ставится (нет готового PyYAML) — вместо него `ruff check . --select S`
  (те же проверки). pip-audit, mypy, pytest, pytest-cov установлены (18.10.2026). Файл
  `.coverage` после `pytest --cov` удаляй — он не для git.
- Android lint: `gradlew lintRelease` (~6 мин) → `android/app/build/reports/lint-results-release.txt`.
- Android: JDK и Gradle — в `D:\Claude\android-tools` (как в `tools/build_apk.py`:
  `JAVA_HOME` = последняя папка `jdk-*`, `GRADLE_USER_HOME` = `gradle-home`), запуск
  `android\gradlew.bat` из папки `android`. Долгие сборки — в фоне.
- Ничего не запускай на настоящих данных пользователя в `%APPDATA%\ToDoro`: для
  `EXPLAIN QUERY PLAN` создай базу во временной папке (scratchpad) через `db.connect()` и
  заполни примерами (`examples.py`).
- Отчёт пиши по-русски, простыми словами: пользователь — не программист. Термины поясняй.

## PYTHON

- Запусти и разбери результаты: `bandit -r .` (безопасность), `pip-audit` (уязвимости
  зависимостей), `ruff check .` (качество кода), `mypy` (типы), `pytest --cov` (покрытие
  тестами). Если чего-то нет — предложи установить.
- Проверь: секреты и ключи в коде, валидацию входных данных, авторизацию и доступ к чужим
  задачам, хеширование паролей, обработку ошибок (не утекают ли трейсбеки наружу),
  небезопасные eval/pickle/subprocess.

## SQLITE

- Все запросы только параметризованные (никаких f-строк и конкатенации в SQL).
- Найди N+1 запросы, запросы в циклах, `SELECT *`.
- Для основных запросов выполни `EXPLAIN QUERY PLAN` и предложи недостающие индексы.
- Проверь использование транзакций при массовых вставках/обновлениях, режим WAL,
  `PRAGMA foreign_keys = ON`, корректное закрытие соединений, миграции схемы.
- Учитывай особенности общих списков в сетевой папке (см. CLAUDE.md): там нельзя
  `journal_mode=PERSIST/TRUNCATE`, а WAL по сети SMB не работает — не советуй то, что
  сломает общие списки.

## KOTLIN / ANDROID

- Запусти и разбери: `./gradlew lint`, detekt, ktlint (если подключены — если нет,
  предложи подключить).
- Проверь: обращения к БД и сети не в главном потоке, корректность корутин и scope (утечки,
  отмена), утечки Activity/Context, хранение токенов (должно быть через
  Keystore/EncryptedSharedPreferences, не в обычных SharedPreferences), HTTPS и
  network_security_config, exported-компоненты в AndroidManifest, логирование
  чувствительных данных, включён ли R8/ProGuard в release.
- Если используется Room — проверь запросы, индексы в `@Entity`, использование Flow, миграции.
- Проверь устаревшие зависимости в Gradle.

## СВЯЗЬ С ТЕЛЕФОНОМ (phone.py)

Сервер слушает домашнюю сеть или VPN — любое устройство рядом может к нему обратиться.
- **Адрес:** на каких сетевых адресах слушает (`Server.__init__`), не виден ли он из интернета;
  что отдаётся без ключа (`/`, `/ping`) — там не должно быть имён, задач, версий.
- **Ключ (токен):** длина и случайность (`secrets`), сравнение за постоянное время
  (`hmac.compare_digest`), задержка при неверном ключе, что «Отключить телефон» стирает ключ и
  сервер перестаёт слушать, что ключ не попадает в журналы и сообщения об ошибках.
- **Входные данные:** каждое поле JSON проверяется по типу и значению (заголовок, срок, минуты,
  колонка, исполнитель, `version`, `client_id`); границы `Content-Length` (отрицательная, огромная);
  разбор адреса (`ROUTE`) — нельзя добраться до чужого списка или файла; ответы на ошибки не
  раскрывают пути и трейсбеки.
- **Устойчивость:** сервер однопоточный — проверь, что медленное или молчащее соединение не
  останавливает его (`Handler.timeout`), а исключения вне `ApiError`/`sqlite3.Error` не оставляют
  телефон без ответа.
- Проверяй опытом: поднимай `phone.Server` на временных данных и свободном порту, как в
  `tests/test_phone.py`.

## ОБНОВЛЕНИЯ (updater.py)

- Скачивание только по HTTPS и только с GitHub (`api.github.com`, `github.com`,
  `objects.githubusercontent.com`) — проверь, что адрес файла из ответа GitHub не может увести
  на другой сайт.
- Подлинность: совпадение размера и SHA-256 (`digest` из ответа GitHub); что будет, если суммы
  нет (ставить без проверки нельзя). Помни ограничение: сумма берётся у того же GitHub — она
  защищает от порчи при скачивании, но не от взлома аккаунта; цифровой подписи у установщика нет.
- Нельзя подсунуть старую версию (сравнение номеров в `is_newer`); куда сохраняется установщик
  и с какими параметрами запускается.
- Запасной путь через WinINet (`_WinInetResponse`) должен остаться: без него обновления не
  работают в корпоративной сети пользователя.

## СЕКРЕТЫ И ЛИЧНЫЕ ДАННЫЕ (репозиторий публичный)

- В текущих файлах: ключи и пароли (`ghp_`, `github_pat_`, `BEGIN PRIVATE KEY`, `password`,
  `token`, `secret`), файлы подписи Android (`*.jks`, `*.keystore`, `signing.properties`,
  `local.properties`), базы с задачами (`*.db`), пути вида `C:\Users\<имя>`, адреса e-mail.
  Проверь и `.gitignore`.
- В истории git — то, что видно на GitHub: `git log --remotes --tags -p` с поиском по тем же
  словам, а также `git log --remotes --tags --format="%an <%ae>"` — авторы коммитов должны
  быть с адресом `noreply`. Локальную ветку `backup-before-email` не проверяй и никуда не
  отправляй — это старая копия истории.
- Личный логин GitHub и личный e-mail владельца (они есть в памяти Claude) не должны
  встречаться ни в файлах, ни в коммитах. В отчёт и в файлы репозитория их не вписывай —
  пиши «найден личный логин/e-mail» и место.
- Если секрет уже попал в историю: не переписывай историю сам — объясни пользователю, что
  секрет надо сменить (перевыпустить), и предложи варианты.

## ЗАВИСАНИЯ ОКНА (поток Tk)

Окно ToDoro — один поток Tkinter: любая долгая операция в нём замораживает окно («белый экран»).
- Найди в `todoro.py` долгие операции, которые выполняются прямо в обработчиках кнопок,
  `after(...)`-циклах и при запуске: сеть (`urllib`, `updater`), общая папка (`team`, `db` на
  соединениях с общими списками, `os.path`/`Path` на сетевых путях), Outlook (COM),
  `subprocess.run`, `time.sleep`, чтение и запись больших файлов (вложения), снимки экрана.
- Всё, что может ждать сеть, должно идти через `in_background()` или `team.Probe`; к общей папке
  окно обращается только по действию пользователя или сразу после свежей удачной проверки
  связи (см. CLAUDE.md, «Rules learned the hard way»).
- Проверяй опытом на временных данных: общая папка — недоступный сетевой путь (например,
  `\\10.255.255.1\share`), и замерь, отвечает ли окно (запуск — как в `tools/make_screenshots.py`).
  Окно встаёт поверх остальных — предупреди пользователя одной фразой.

## После отчёта

Жди подтверждения пользователя, прежде чем вносить изменения.

**Все исправления по аудиту — в отдельной ветке `audit`, не в `main`.** Это правило сильнее
общего правила проекта «коммит и push в main после каждого изменения».
1. Перед первой правкой: `git switch main`, `git pull`, затем `git switch -c audit` (если ветка
   `audit` уже есть — `git switch audit` и `git merge main`, чтобы взять свежий `main`).
2. После каждого исправления: `python -m unittest discover tests` (для Android — сборка и
   тесты), коммит с русским сообщением в ветку `audit` и `git push -u origin audit`. Заметные
   пользователю правки записывай в `RELEASE_NOTES.md` под `## Не выпущено` — тоже в ветке `audit`.
3. В `main` сливай **только после явного разрешения пользователя** («слей в main» и т. п.).
   Тогда: прогони тесты в `audit`, `git switch main`, `git pull`, `git merge --no-ff audit`,
   снова тесты, `git push`. Ветку `audit` после слияния не удаляй без спроса.
4. В конце работы скажи пользователю, что исправления лежат в ветке `audit` и ждут его
   разрешения на слияние в `main`; дай ссылку на сравнение веток:
   https://github.com/machinist-soft/ToDoro/compare/main...audit
